# Firebase setup

This project ships with the full Firebase integration (Analytics, Crashlytics, Performance
Monitoring, Remote Config) already wired in code, but it stays **inert** — the app builds and
runs exactly as before — until you connect a real Firebase project. Nothing else in this project
can do that step for you: it requires your own Google account and a few clicks in the Firebase
console.

## Why the app doesn't just "have" Firebase already

Firebase identifies your app via a `google-services.json` file, generated by the Firebase console
for one specific project + one specific `applicationId`. That file isn't something that can be
fabricated locally — it has to come from a real project you own. This repo does not include one
(and it should never be committed once you add it — see below), and `app/build.gradle.kts`
conditionally skips applying the Firebase Gradle plugins when it's absent specifically so the
project keeps building cleanly without it.

## Steps

1. Go to the [Firebase console](https://console.firebase.google.com/) and create a new project
   (or pick an existing one).
2. Add an Android app to that project with application ID **`com.suman.memoryarchitect`**
   (must match `app/build.gradle.kts`'s `defaultConfig.applicationId` exactly).
3. Download the generated **`google-services.json`** and place it at:
   ```
   app/google-services.json
   ```
4. In the Firebase console, enable the products you want (Analytics is on by default when you
   create the app; Crashlytics and Performance Monitoring each have a one-click "enable" the
   first time your app sends data).
5. Add `app/google-services.json` to `.gitignore` if this project is ever put under version
   control — it's environment-specific, not something to share across machines/forks.
6. Rebuild (`./gradlew assembleDebug`). No other code changes are needed — the next build detects
   the file, applies the Firebase Gradle plugins, and every event this project already logs starts
   flowing to your project's Analytics/Crashlytics/Performance dashboards.

## What works before you do this

Everything. `FirebaseAvailability.isConfigured` (`core/analytics/FirebaseAvailability.kt`) is
`false` until the file exists, and every Firebase-backed class in `core/analytics/` checks it
before touching any `Firebase.*` API — so the app runs normally, gameplay is completely
unaffected, and analytics calls silently no-op instead of crashing.

## Known limitation: Performance Monitoring's automatic instrumentation

As of this writing, Firebase's Performance Monitoring Gradle plugin
(`com.google.firebase.firebase-perf`) does not support Android Gradle Plugin 9.x — it depends on
an AGP API (`com.android.build.api.transform.Transform`) that AGP 9 removed, and fails to apply at
all. This is an open upstream issue
([firebase-android-sdk#7293](https://github.com/firebase/firebase-android-sdk/issues/7293)), not
something fixable from this project's side by picking a different plugin version — there is no
released version that supports AGP 9 yet.

`app/build.gradle.kts` has a single `enableFirebasePerfPlugin` flag (currently `false`) gating
this plugin specifically, independent of Analytics/Crashlytics — Analytics and Crashlytics both
apply and work normally regardless of this flag. Once Firebase ships an AGP-9-compatible release,
flip that one flag to `true`.

**This does not remove Performance Monitoring entirely.** The plugin's job is *automatic*
bytecode-woven instrumentation (screen rendering time, network request timing) — without it,
those two automatic traces aren't collected. The manual custom trace this project already logs
(`level_load`, around on-device level generation — see `core/analytics/PerformanceTracer.kt`)
is a plain SDK API call (`Firebase.performance.newTrace()`) that doesn't need the plugin at all,
and works today.

## Remote Config note

This project's live remote-config values (ad cadence, difficulty base, etc.) currently come from
the dev mock backend (`RemoteConfigRepositoryImpl`, `mock-backend/index.js`), not Firebase Remote
Config — that's real, working infrastructure and this integration doesn't replace it. A
Firebase-backed source (`core/analytics/FirebaseRemoteConfigSource.kt`) is wired and ready
alongside it (per the "prepare architecture even if not immediately used" ask) for whenever you
want to migrate off the mock backend for a production release.
